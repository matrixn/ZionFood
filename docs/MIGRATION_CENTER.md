# GloriaFood Migration Center — 0.0.45

Access: restaurant dashboard → Connections → Migration Center. Requires a verified owner/manager with menu management permission. Platform administration alone is insufficient. Each import belongs to one organization and location.

## Flow

1. Generate the location Fetch Menu key in GloriaFood (Others → 3rd party integrations → Enabled integrations → Fetch Menu). Paste it into the masked field. The backend contacts only `https://pos.globalfoodsoft.com/pos/menu`, using Authorization, JSON and API version 2. Alternatively upload an already exported JSON file (maximum 5 MiB); there is no manual JSON editor.
2. Select size-price semantics (product + adjustment, or absolute size price), fallback nutrition basis and tax basis points. No currency conversion is attempted. Explicit source nutrition basis takes precedence over the fallback. Confirm authorization.
3. The queued fetch leaves the public menu unchanged. The page polls its selected import automatically and shows a completion toast. The report shows source/category/product counts, issues, rules/defaults, exact integer prices, nutrition, source differences and source-derived example baskets. A fresh report can be downloaded as JSON or opened in a print view and saved as PDF by the browser.
4. Resolve unnamed nutrient IDs using selectors; revalidation uses the encrypted source without a second provider request. No nutrient IDs are guessed. Confirmed mappings from the most recent published import for the same source restaurant/location are reused on reimport; they remain in report evidence. Unknown allergens/tags/units or malformed prices remain blockers; correct the source and import again. Named nutrients accept supported English aliases and canonical keys. All fourteen canonical allergen groups and eight documented dietary labels are represented.
5. If a public FoodBooking link was supplied, compare each optional restaurant-setting proposal and select only the fields to apply. All choices start unchecked. Delivery zones are append-only; existing rows are retained. Unsupported settings are unavailable individually. Review food declarations, every variant price, selection bounds and warnings against the real source. Confirm the report and resolve local-edit conflicts. A confirmation dialog publishes transactionally. Approval does not bypass blockers. A stale review fingerprint returns 409 and requires a fresh preview.
6. Test pickup/delivery/table-service availability and kitchen receipt with the restaurant’s actual configuration. Source order types still intersect with enabled location services; imports never enable services or payments.

## Compatibility matrix

| GloriaFood field | Implemented behavior |
| --- | --- |
| Categories/products/descriptions | Canonical staged tree, explicit source IDs, location-specific published version |
| Product/size prices | Decimal-to-integer conversion (at most two decimals), selected additive/absolute normalization, currency/range blockers; checkout uses stored prices |
| Sizes | Absolute local price, default flag, availability, size nutrition and own modifier groups; editing preserves variant IDs and existing nutrition |
| Category groups | Explicit relation; inherited by every product/size; editable in category dialog |
| Product groups | Existing relation, combined with category and selected-size groups, deduplicated by local group ID |
| Size-specific groups | Explicit variant relation; only the selected variant’s options can be ordered; editable per variant |
| required/force_min/force_max | Required group needs at least one and its minimum; optional group permits zero, otherwise its minimum applies; bounds count distinct selected options |
| allow_quantity | Each selected option has 1–50 units (per-option maximum), multiplied into each product unit price and snapshotted; non-quantity groups permit exactly one |
| default | Default size and options initialize the configurator; invalid defaults are blocked; customers may change them |
| Allergens/tags | Canonical local food data, named mapping, conflicting labels blocked and explicit restaurant confirmation; existing food editor/AI review remains available |
| Nutrition | Structured product and variant data, basis/units/ranges validated; unnamed IDs require explicit nutrient mapping; original raw data retained encrypted |
| Order types | Nullable unrestricted list or explicit pickup/delivery/dine_in set (empty list disables all); UI editor and authoritative checkout enforce it |
| Internal kitchen names | Product/option internal names imported; immutable order snapshots retain public and internal names; KDS uses internal names and quantity |
| Photos | API does not document photo export; existing local photos retained on reimport, upload supported in product editor; no remote URL downloads |
| Hours/delivery | Existing setup retained, reviewed separately; no fabricated source settings |

No structural entry from the original partial/incompatible matrix is left unsupported. This is compatibility for the documented contract, with explicit resolution for ambiguous data, not a claim that every undocumented provider extension can be imported automatically.

The official fixture has four products, four sizes, five group appearances and ten option appearances. Its size nutrition uses IDs 9–14 with no nutrient names. Documentation does not establish those ID meanings; tests deliberately supply a test-only mapping rather than presenting it as authoritative. The fixture’s base 7/size 2 is handled by an explicit price-mode choice. Distinct-option bounds with quantity pricing are shown for confirmation; real restaurant behavior must be checked before production cutover. Undocumented active periods, promotions and availability fields are flagged as not interpreted.

## Reimport and rollback

Publication creates a new menu version and switches only the selected location’s assignment. Shared original menus and other locations stay intact. Old menu/product rows remain available; order snapshots and QR/menu entry URLs are preserved. Publish/rollback commit the existing menu.updated outbox event only for the changed location. Retired-version imported groups are hidden from the active editor catalogue. Entity mappings contain provider/source restaurant, location, entity type, hierarchical external ID and publication batch; each live version has one mapped product per source ID. Inactive retained versions intentionally retain their own rows.

Reimport compares the original canonical source with its predecessor and fingerprints current local products, categories, rules, ingredients, content, images and sizes. Locally changed products require keep-local/use-source decisions. Keep-local copies the full product graph (including inherited rules, nutrition and photo); source-removed and locally added products are retained by default. A locally deleted product stays deleted when preserved. The interface reports source additions/changes/removals. Conflicts are resolved at product granularity, not by merging individual text characters or individual price fields. Source replacements keep existing photos and ingredient associations. Removed source products are not silently deleted.

Rollback restores previous location menu assignments only if the published menu graph and assignment still match the publication fingerprint. It refuses later local edits or a newer publication. It never deletes historical orders or rows. Menu versions are retained; there is no destructive automatic publication-history cleanup.

## Storage/security/operations

Tables: import_batches, import_snapshots, import_issues, import_reports, import_entity_mappings and import_publications. Source/canonical snapshots and queued keys use Laravel encryption. Reports contain no key. Queue payloads contain only a batch ID. Credentials are cleared on success/failure; stale queued keys expire after one hour via `zionfood:imports-prune`. Unpublished ready/failed snapshots expire after `ZF_IMPORT_RETENTION_DAYS` (default 30). Published evidence is retained for audit/reimport; define an organization retention policy before broad launch.

Provider transport has a fixed HTTPS URL, verified TLS, disabled redirects/proxy, five-second connect/30-second total timeout, and five-MiB header/body/stream bounds. No arbitrary endpoint is accepted. Fetch jobs have one attempt; a new import explicitly retries a failed fetch. Logs include batch ID, exception class and processing stage; validation failures add bounded sanitized field paths and rule names, without credentials, source values or response bodies. Secret inputs are excluded from validation flash. File parsing uses bounded size/depth; canonical counts cap categories, products, sizes and options. Failures never mutate the public menu. Report routes repeat tenant/location authorization. Publication takes organization location locks in a consistent order, then the batch lock, and uses a transaction. Product/category/modifier management and product removal share the location locking convention to serialize menu writes with publication. Menu caches clear after commit.

Deploy the additive migration and built assets through the normal release process; ensure Horizon processes default jobs and restart workers through that process. Run Laravel scheduler for pruning. Set PHP/web upload limits at least 5 MiB if offering the maximum file size. No live key is required in .env; keys are supplied per restaurant/import. This change performs no manual deployment or external credential setup.

## Acceptance and limits

Automated tests cover official payload ingestion, unknown-ID resolution, precise server pricing, quantity snapshots, defaults, category/size isolation, local-edit reimport, guarded rollback, stale previews, tenant boundaries, credential lifecycle, file input, a 300-product menu and a second location. Provider HTTP is simulated; browser file import uses the actual backend. Example baskets are evidence, not exhaustive combinatorial certification. The operator can print the report to PDF; no server PDF engine/dependency is installed.

A real Fetch Menu request using a restaurant-authorized key and full cutover acceptance are still required. CSV/XLSX/XML/PDF/OCR adapters, bulk photo matching, customer/order-history migration, automated external source order comparison, field-level conflict merges and marketing migration landing pages are separate follow-ups. Existing AI translation does not imply translation export from Fetch Menu; the documented API provides no multilingual export schema.

## 0.0.33 generated-evidence budget

ImportVerification checks cumulative generated work incrementally during normalization and again before allocating baskets: at most10,000 baskets,50,000 selected choices including category/product/size inheritance, and8MiB conservative escaped JSON evidence bytes. ProcessImport generates accepted evidence before the snapshot transaction. Upload, provider fetch and revalidation share this boundary. Excess fails explicitly as import_complexity_limit with RO/EN guidance, without silent truncation, publication or replacing previous staged snapshots. This is an additional workload bound; existing source/cardinality limits and authorization remain. Large simple menus remain supported, while particularly complex menus must be simplified or split. The same valid1.33MB input that exhausted a256MiB isolated baseline PHP process now rejects in a controlled manner under the same ceiling.

## 0.0.39 optional provider restaurant identity

The latest user-provided Forge diagnostic identifies the concrete rejected field: `restaurant_id` with rule `required`. The official v2 documentation and sample include that field, while this restaurant's actual response omits it. Adapter 1.0.1 therefore accepts absence, null or an empty string; supplied nonempty IDs still require a positive integer. Menu `id` remains required. This is a targeted compatibility change, with all other validation retained.

A first import lacking the field uses `menu:<source menu id>` for its source namespace. Before staging or publishing, ResolveImportSource looks only at published batches for the same organization, target location and source menu ID. A unique established numeric identity or fallback namespace is reused. When the provider subsequently supplies its restaurant ID, it is recorded separately as reported/resolved metadata without rewriting the namespace or original encrypted source. This preserves prior product comparisons, retained images/ingredients, nutrient mappings and explicit keep-local decisions. Neither API keys nor key hashes identify menus, so rotating keys does not change lineage. Older reports without the new metadata can resolve from their numeric source namespace. MariaDB JSON-null strings are normalized before identity comparison.

If history contains multiple known restaurant identities for the same menu ID, an import omitting restaurant_id receives a blocker instead of merging sources. A supplied different restaurant ID starts an independent lineage. Publication resolves identity again under the existing menu-write locks and rejects a stale alias with HTTP 409, requiring a new import. There is no claim that provider menu IDs are globally unique; the namespace and history are scoped to the target organization/location. Cross-location and cross-tenant imports do not share lineage.

Validation issue titles and field/rule labels now render separately in RO/EN; internal codes remain unchanged. Already failed batches retain their diagnostic evidence and cannot be retried with the discarded key. After the normal release/worker restart, initiate a new import using the restaurant's Fetch Menu key. The current change uses simulated provider responses and browser file imports; it does not establish that every other field in this restaurant's live menu is compatible. No real key, public request or production database was used for these checks.

## 0.0.40 optional public-menu photo enrichment

Migration Center accepts an optional public FoodBooking URL for API-key and JSON-file imports. Supported links use HTTPS on foodbooking.com/www.foodbooking.com, /ordering/restaurant/menu or /ordering[/], with a single restaurant_uid UUID query parameter. An omitted/empty URL performs the original import with no public-menu request or photo job. No arbitrary URLs, credentials, ports, extra queries or fragments are accepted.

The public widget was inspected with anonymous browser network capture. It initializes via POST https://www.foodbooking.com/api/cart/init with restaurant_uid and an initial website payload. A direct backend request without a cookie jar or Fetch Menu key was also verified. This is an observed public widget interface, not a documented/stable partner API. If it changes or becomes unavailable, the optional enrichment reports a warning and retains the base menu. No checkout, real order, account login or access-control bypass is performed.

Fetch Menu remains authoritative for every category, product, price, modifier and food declaration. The public response must match the source menu ID/currency and any known restaurant ID. A mismatch blocks publication and never selects photos. Matching uses an exact item ID, typed picture key and picture entity_id, with trimmed exact names checked whenever the product is listed publicly; duplicate public IDs, renamed products and missing/invalid picture entries are skipped rather than guessed. Public menu counts need not equal Fetch Menu counts. Regression coverage explicitly retains 386 products/24 categories with a smaller public subset; a link must never filter the authoritative import. Public restaurant name/address/contact/location/cuisine metadata is restricted to an explicit allowlist and shown for review, without changing restaurant/location settings.

The widget stores photo records in restaurant.pictures under menu_item-<product id>, with entity_id, filename and density. We select full product images, not category/promotion photos or records for products absent from Fetch Menu. A picture may belong to a source product omitted from the visible public list; the source product ID and picture entity_id still provide an exact association. Duplicate public IDs or names that conflict when available prevent selection. The observed renderer appends _d2/_d3 before the extension for density variants; the real larger JPEG checked was 1005x675 rather than its 335x225 base image. Images come exclusively from the fixed www.fbgcdn.com/pictures/ destination. Supplied CDN-base fields are never trusted as download destinations.

Source normalization/evidence validation happens before enrichment. Exact matches become an encrypted pending manifest in the canonical snapshot; raw Fetch Menu snapshots remain unchanged. The batch enters enriching and DownloadGloriaFoodPhotos processes five concurrent downloads per job on the existing default queue. Each job has one attempt and a 30-second timeout, retaining the existing Horizon/queue timeout configuration. A batch-row lock serializes duplicate jobs, each completed source entry is removed from the pending manifest, and another ID-only job continues the next chunk. A finished duplicate is a no-op. The UI polls queued/enriching batches automatically and shows matched/downloaded/missing/failed/limited counters and tenant-authorized local thumbnails, without enabling publication until ready. Failed dispatch/worker execution or an hour without progress preserves completed images and returns a ready import with explicit incomplete-photo warnings; no automatic unbounded retry. The normal scheduler runs recovery/pruning.

Every provider/CDN request revalidates all DNS A/AAAA answers through the existing globally-routable destination policy and pins cURL to a checked address. TLS verification stays enabled; proxies and redirects are disabled, with fixed hosts, validated filenames, bounded connect/total timeouts and response-header/body/progress caps. Public JSON is at most 5 MiB; each image response is at most 3 MiB; cumulative recorded photo traffic stops at 128 MiB per import (a bounded in-flight chunk can already be downloading). Only JPEG/PNG/WebP MIME and decoded raster formats are accepted, up to eight million pixels/8192 pixels per edge. GD re-encodes WebP, strips source metadata and rejects invalid/oversized outputs. Unknown extra JSON fields, trackers, customer/device/cart/payment data and provider credentials are not imported.

Staged files live on the private local disk at imports/<batch ULID>/photos and are served through a repeated organization/location-authorized preview route with private/no-store and nosniff headers. No remote image URL is used as an img source in the app. Preview reports include source URL, metadata/counters and photo dimensions/checksums. Revalidation reuses the staged snapshot/files without refetching. Publication verifies private paths and SHA-256 bytes, then copies accepted photos to the public disk; newly created files are cleaned if publication rolls back. Cleanup retains any file already referenced by a committed menu if a later cache callback fails; cleanup failures are logged and do not replace the original exception. Existing ZionFood photos are preserved even when source fields are replaced, and keep-local preserves the full local graph. Unpublished private photo directories expire with snapshots; published evidence/files remain for audit and history.

Live local verification used the supplied public page for La Trattoria Valcea: menu 169612, restaurant 170737, nine public categories/109 products, 48 exact product photos and 61 without matching photos. The final queued implementation staged all 48 WebP images, zero failed/limited, 7,174,358 source image bytes, in 22.14 seconds in the isolated sync-worker harness. A preliminary single-request time budget staged only 35; it was replaced by resumable five-photo jobs before final validation. The native Windows PHP cURL CA bundle was missing; a private test-only bundle from system trust enabled verified TLS. No TLS bypass or global PHP/.env change was made. This confirms public-page enrichment locally, not the user's 386-product Fetch Menu payload or a production Forge/Horizon deployment. Other source fields still require normal migration verification. See CODEX_PROGRESS.md for final automated/browser checks.

## 0.0.41 opt-in restaurant settings

The verified public response can now propose five independent groups: shared restaurant name; location address/city/postal code/country/map pin; shared public phone plus the selected location setup phone; weekly opening hours with source time zone; and append-only delivery zones. Nothing is preselected. An empty public URL keeps the prior import flow; a URL with no selected settings still leaves all restaurant configuration unchanged. Old snapshots lacking normalized settings candidates need a new import to expose these groups. Photos remain a separate enrichment from 0.0.40.

NormalizePublicRestaurantSettings converts only allowlisted source fields, validates lengths/formats/coordinates and stores immutable candidates with per-group availability in the encrypted canonical snapshot. Names/phones show every restaurant location affected by their shared scope. The preview shows existing/proposed values, all seven days, timezone, fee/minimum-order amounts and read-only Leaflet polygon outlines. The source physical address is distinct from legal-company fields. Source latitude/longitude update the saved restaurant pin only with the address choice; absent source coordinates clear a stale pin on approval. Phone updates the public brand and the current location wizard. Shared-name updates synchronize sibling wizard names and increase setup revisions. No services, ordering switches, reservations, tables or payments are enabled by this import.

Supported hours are validated opening-type weekday bitmasks (bit0 Monday through bit6 Sunday, 127 all days), one same-day interval per day and an IANA timezone. Identical duplicate intervals collapse. Split, overnight, 24-hour, service-specific schedules and date exceptions are marked unavailable instead of widened/approximated. The captured restaurant uses mask127 and 11:00–23:00 daily, so no individual-day bit mapping was independently verified against a second live provider account. Preview and source review remain required.

Zones require unique positive source IDs, delivery usage, fixed fees and valid simple polygons of at most200 vertices. Source lat/lng objects become closed GeoJSON longitude/latitude rings using the existing Polygon validator. Decimal fees and minimum orders convert exactly to integer minor units; no currency conversion or floating-price estimate is used. Circles, polygon holes, unrecognized shape extensions, variable rates and invalid geometry/money make this group unavailable. Appending must keep the target at no more than30 zones. Existing zone rows, active flags and precedence are preserved; added rows follow existing priority. No source omission deletes a target zone.

For idempotence, delivery_zone mappings retain provider/source/location namespace and external IDs. Already mapped zones keep their current configuration even after local name/fee changes. Identical existing/source entries are linked rather than duplicated. Equivalent source entries can share one new row. Missing previously mapped rows can be imported again when selected. The normal Settings editor now retains submitted scoped zone IDs and refreshes IDs after each save, preserving these associations and inactive states; foreign/duplicate IDs are rejected. Manually removing zones in the standalone editor remains an explicit operation outside the append-only import.

Approval accepts only setting-key selections, never replacement values from the client. Owner/manager and menu-write authorization are repeated in the domain helper; changing hours/zones additionally requires order management. The existing organization-location locks and a restaurant-row lock protect shared writes. The review fingerprint includes current relevant restaurant settings, setup fields, hours and zones; a change since preview returns409. Refresh preview updates the current side without refetching the provider and clears confirmation. Settings and menu publication share a transaction, so a failed publication cannot leave partial settings applied.

The additive nullable import_publications.settings_snapshot migration stores encrypted organization/location/restaurant-bound before/after evidence plus IDs of newly added zones. JSON/print reports retain selected before/after values; published/reverted UI views show that frozen comparison for selected fields. Returning to the previous menu restores selected settings only if their after-state still matches, preserves later unselected edits and deletes only unchanged zones created by that import. Any selected-field edit blocks automatic rollback. Old publications have a null snapshot and retain prior menu-only rollback behavior. Existing orders/reservations and immutable historical snapshots are untouched.

Release operations: run the additive migration with the normal release process before serving the new code, build assets and restart Horizon normally. No provider credentials or new environment variables are required. Controlled tests use the previously captured public response (including its real program/polygon), a separate private SQLite database and HTTP fakes; this release did not modify Forge or the public restaurant. See CODEX_PROGRESS.md for checks and limits.

## 0.0.42 optional logo

The public-menu simulation adds a sixth, independent **Logo restaurant** choice, unchecked by default. Its current/proposed images use contain sizing, without stretching/cropping. Help explains explicit replacement and the shared scope across all restaurant locations. The confirmation lists the logo only when selected. Unselected/missing/unsupported logos leave existing branding unchanged, including menu-only publication and reimports.

The normalizer recognizes only explicit `pictures.restaurant_logo` or `pictures.logo` records whose thumbnail type matches, whose entity is the source restaurant or zero, and which do not belong to a theme set. Accepted filenames are UUID-shaped JPEG/PNG/WebP with optional provider density variants. Arbitrary URLs, filenames, theme/cover/product images and platform logos are not inferred as restaurant logos. This is a conservative adapter convention, not a claimed documented provider logo API: the captured real public restaurant response has no such record. Positive logo behavior is verified with controlled provider-shaped fixtures and still needs confirmation against a real restaurant exposing a distinct logo. When none is available, the UI explains that the existing logo is kept and offers the normal Restaurant identity upload workflow in its guidance.

The ID-only existing image job includes the logo in its bounded chunks, traffic and pixel limits, using the same fixed CDN, all-answer DNS validation, address pinning, TLS verification and disabled proxies/redirects. Product-photo metrics exclude the logo. A stopped worker or invalid/download-failed logo becomes an unavailable optional choice, not a publication blocker. Valid raster bytes are re-encoded WebP, stripping metadata while retaining alpha and source proportions. Raw SVG/HTML are never served. Source URLs are not used as browser image sources.

Preview bytes remain on private storage under the batch; the new `/app/locations/{location}/migration-center/{batch}/logo` route repeats organization/location/menu-management authorization and uses private/no-store/nosniff headers. Successful staging alone never writes a public logo. Approval accepts only the `logo` setting key, uses the staged checksum-verified bytes, and ignores client logo paths. The review hash includes the existing shared logo path. Selected replacement, encrypted before/after evidence and menu publication share a transaction. Previously staged imports without a logo candidate retain their original options.

The previous logo file is retained, so guarded rollback can restore its path; any later selected-logo edit blocks automatic rollback. Copied logo files are removed on transaction failure, while files referenced by a committed restaurant are preserved if an after-commit cache callback fails. Existing share-image generation continues to contain the whole logo; changing logo paths naturally selects a new share-image cache key. No schema, dependency or environment changes are needed beyond the already-required 0.0.41 migration. See CODEX_PROGRESS.md for executed local checks and production limits.
