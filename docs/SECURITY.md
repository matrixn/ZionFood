# Security boundaries and limits

TenantAccess, Policies, explicit queries, composite foreign keys and Action checks form the isolation boundary. Integration ability checks supplement membership and location access. Staff cannot manage menus or settings; platform admins cannot operate a restaurant without membership.

Fortify handles authentication, email verification and password resets. New passwords require at least 12 characters. Login is limited to five attempts per minute by normalized email/IP. Browser operations use session authentication and CSRF middleware; external integrations use expiring, hashed Sanctum tokens. Real SMTP delivery is not verified locally: the default mailer logs messages to private storage.

Checkout limits are ten requests per minute per IP and 120 per minute per location. `ZF_CHECKOUT_IP_LIMIT` supports deliberate operator tuning; benchmark environments override it because many virtual customers originate from one IP. Tracking is limited to 60 requests per minute per IP. Reverse proxy configuration must preserve the correct client IP without trusting arbitrary forwarded headers.

Checkout recalculates prices from current assigned menus, checks quantities/modifiers/fulfillment/trials and stores snapshots transactionally. It locks the location for idempotency, and status changes use order locks plus optimistic versions. Validation failures cannot create partial orders.

Tracking tokens use 64 random alphanumeric characters. They are hashed for lookup, encrypted for replay, and are not included in order API Resources or logs. The customer page keeps the token in session storage and sends it in Authorization headers. It does not expose a public broadcast channel. Session-storage tracking is limited to the placing browser/tab; a portable customer tracking link is not implemented.

Private broadcasts carry identifiers and versions without names, addresses, phones or notes. Reverb uses an explicit origin allowlist. Horizon authentication requires platform-admin access even in local environments. Unknown Host values are rejected. Storefront/API hosts cannot open central dashboard or authentication routes; production host allowlists must be set explicitly.

Uploads have type, size and dimension limits, randomized storage filenames and organization storage prefixes. SVG is excluded. Configure Nginx so public storage never executes PHP. No arbitrary upload path is accepted. Current validation does not re-encode raster images or run malware scanning.

Webhook delivery accepts only public DNS HTTPS destinations on port 443, with no URL credentials/query/fragment. Each attempt rejects unsafe or mixed public/private DNS answers, pins the checked IP through an explicitly selected cURL transport, verifies TLS/hostname, disables redirects and environment proxies, and bounds connect/total timeout and response size. Signing keys are encrypted and never returned in existing configuration. HMAC covers the timestamp and exact body. Delivery leases, stable event IDs, six bounded attempts and the scheduler provide at-least-once recovery; receivers must verify signatures/timestamps and deduplicate. History stores only bounded status/failure metadata, not response bodies or transport exception messages. See STAFF_BRANDING_LOCALIZATION_WEBHOOKS.md.

No payment-card processing, fiscal certification, automatic billing, MFA, data-retention automation or full audit trail is claimed. Order history is immutable through the model, not against direct SQL writes. Production TLS/DNS, backups/restores, SMTP and sustained capacity require deployment verification. Never commit `.env`, demo credentials, integration tokens or private fixture files.

Staff invitation tokens are hashed and expire after seven days. An email-bound token proves the invited address during prepare/accept; the fragment is removed and an encrypted server-session proof can bind registration to the invitation. An unverified account is verified only when that exact emailed proof is accepted under current role/scope/revocation checks. Queued invitation notifications are encrypted and skip revoked/obsolete invitations. Owner access cannot be altered by this management UI; managers cannot create or edit manager/owner roles. Membership removal immediately denies authoritative API access and revokes organization-scoped tokens. Existing identifier-only WebSocket subscriptions may persist until reconnection; forced socket disconnection is not implemented.

Language preferences accept only ro/en and use an encrypted HttpOnly SameSite cookie plus account storage. API schema keys and enums remain locale independent. API and private-channel authentication use the current XSRF cookie after login/session rotation.

Cuisine catalogue editing is platform-admin-only; tenant managers may only select available entries for their own location. Selection retains revision/row-lock checks and a composite tenant pivot FK. Photos are bounded JPEG/PNG/WebP uploads, stored under generated paths; arbitrary image paths and SVG are not supported. Source/license URLs are passive HTTP/HTTPS links, never runtime server fetch targets. The default catalogue and credits are bundled, requiring no network access at migration time.

Restaurant address search is restricted to verified tenant owners/managers for their location. The client supplies address fields, never a destination URL. Only address components are forwarded to the server-configured HTTPS provider, with TLS, no redirects/proxy, bounded timeouts/body/results and shared cache throttling. Warning logs omit the query and response. Private provider configuration is not part of public maps props. Candidate labels are rendered as escaped text; lookups cannot persist changes on their own.

Reverse lookup uses the same authorization and bounded transport, forwarding only the pin coordinates. Nearest usable results are limited to 200 metres; structured strings are bounded and missing fields explicit. Stale responses after pin/address changes cannot apply. A new feature-cache namespace isolates incompatible older formatted results.

Inline setup editors reuse the same authorized WorkspaceController data builder as standalone pages. Foreign/staff access to wizard administration remains denied. Locations are restricted to the existing accessible collection, and configure links require management rights; destination routes recheck authorization. No role grants or tenant transfers are introduced.

Ingredient scopes are derived server-side from the authenticated location/category, never from payload IDs. Platform admin manages global records; owners/managers manage their own restaurant entries. Staff, foreign tenants and another restaurant within the same organization cannot inject custom ingredients. Hidden/deleted ingredients are rejected on new assignments but existing recipe associations may be retained or removed. Product writes, pivots and validation share a transaction. Public payloads omit owner/source/review metadata; text is Vue-escaped. The PDF is build-time source material only, not runtime executable input.


## Storefront experience (0.0.12)

Anonymous checkout reverse lookup accepts only valid coordinates inside an active polygon for an accepting delivery location. Verified custom hosts cannot lookup another location. IP/minute, IP/hour and location/minute limits supplement the shared provider cooldown/cache. No customer names, phone numbers or typed addresses reach the reverse provider. The UI discloses coordinate forwarding. Client-side validation and cart image paths do not influence authoritative checkout pricing, zone or authorization.


## Company lookup and friendly public routing (0.0.15)

ANAF lookup is available only to verified owners/managers for their own location. The upstream HTTPS URL is fixed; clients cannot supply provider URLs or credentials. Transport disables redirects/proxies, verifies TLS and bounds connection/read/overall time, JSON depth and response bytes. Only CUI and reference date are sent. Results must match the requested CUI. Logs omit CUI, business contact data and provider content. Five attempts/minute and fifty/hour per user supplement the global provider lock and one-second cooldown; positive/negative results are cached. Private legal details never become public storefront props.

Slug routes resolve only locations belonging to that restaurant; mapped storefront hosts remain pinned to their configured location and cannot enumerate other brands/branches. Unknown/inactive tables and foreign-host access still return 404. Known disabled or paused table menus display no session/customer data and do not grant a token or bypass service/hour/checkout checks. Rotation does not reopen a table or enable its service.

Invitation prepare requires the secret fragment proof before revealing email. Pending session proof is additionally encrypted and revalidated at registration. Email matching, inviter permissions, scope, expiration/revocation and membership creation remain authoritative under database locks. Registration and acceptance run in one transaction. No client invitation flags or supplied verification timestamp can bypass normal registration verification.


## Feature capabilities and table batches (0.0.16)

Organization membership capability matrices supplement role, location scope and token abilities. Request-driven reads/writes, policies and domain actions enforce the relevant view/manage level. Separate kitchen list/transition routes avoid using order-history permission as a proxy: the kitchen list always excludes terminal orders, even with `active=0`. Order WebSocket subscriptions require orders or kitchen view; events remain identifier-only. Existing subscriptions may persist until reconnection, while authoritative API requests recheck current membership permissions. Queue/list UI clears retained data on authentication/authorization failure. Owner protection and manager delegation ceilings are preserved.

Menu mutation checks every affected shared-menu location; modifier library changes need all organization locations. Setup seating/service/reservation and QR-cutoff writes also guard their corresponding capabilities. Bulk table selection is constrained to the authorized location and explicit scope; arbitrary foreign table IDs or room labels cannot select another venue. Location locks align batch operations with individual QR open/close/rotate and guest connection. Transactions preserve all-or-nothing changes, close affected sessions and retain QR secrets/orders. Manual activation never bypasses service/program/cutoff checks.
## Menu content and AI (0.0.17)

Feature/location/shared-menu authorization is required for every content save, import staging, generation and approval; worker execution rechecks the requester. Platform-only AI configuration is separate. Keys and draft snapshots are encrypted, keys are hidden/excluded from flashed input, provider endpoints are fixed HTTPS with TLS, no redirects/proxy and bounded time/bytes/tokens. Provider replies are untrusted, strict-schema requests are revalidated, and no model output can alter price/IDs or publish nutrition. A global database lock serializes the request budget and the queue paces provider calls. Interrupted attempts fail visibly rather than silently creating duplicate billed requests. Review source hashes protect against stale publication. Public payloads omit private recipes/references/reports. Imported unknown allergens require editor correction; provider internal IDs are not assumed to be regulatory group numbers. This feature does not certify allergy absence, dietary claims or reference-data accuracy.

Migration Center uses verified tenant-manager sessions plus menu-write permission for every route. Fixed TLS provider transport, redirect/proxy suppression, bounded parsing/responses, encrypted ephemeral keys/snapshots, safe error codes and stale-secret pruning are required. Publication and rollback must lock the correct location, preserve shared menus and historical orders, refuse stale fingerprints and never bypass unresolved blockers. Reports must exclude credentials.

Guest table-order receipts require the exact table/location/session bearer and return only nonterminal dine-in snapshots. The permanent QR credential, a new session or a different storefront host cannot read earlier sessions. Existing receipt capabilities intentionally survive ordering closure/expiry/rotation until orders become terminal; they never authorize new checkout. Do not expose contacts, notes, tracking credentials or internal kitchen names through this public receipt endpoint. Tokens remain outside URLs; responses are private/no-store and throttled.

## 0.0.24 operational boundaries

Table summary/detail access requires tables read plus independent orders or kitchen read. Serving requires orders/kitchen manage and the existing order version/state transition; table-only employees receive no order totals/products. Organization/location/table/session scopes are applied on both sides of the order-session join. Reservation menu return targets are server-derived after bearer and mapped-host checks.

Error-alert administration requires is_platform_admin and a verified browser session/CSRF; tenant ownership alone does not grant this global setting. Bounded database windows/row locks and generation headers suppress old alert backlog after manual resume. Failed/uncertain submissions conservatively use the attempt budget; this protects delivery volume but does not guarantee delivery. Original error logs continue while alert emails are suspended. MAIL_ERROR_ALERTS remains a master disable. No raw broadcast transport messages/URLs/credentials enter the added diagnostic logs; TLS verification remains enabled.

0.0.25 retains failed outbox events while bounding total work per delivery cycle under a row lock. CLI recovery has no HTTP route and requires a known exhausted event. Reverb signed URLs are excluded from propagated exceptions and diagnostic outputs, including previous-exception chains. The DNS/configuration command validates hostname syntax before printing and never publishes a message, prints a key/secret or disables TLS verification.


0.0.26 restricts all email metadata/provider/index endpoints to verified platform admins and uses explicit serializers excluding bodies/tokens/credentials/context. Private metadata fields are encrypted, exact recipient search is keyed, and only authenticated encrypted application queue payloads may be indexed. Backend usage requests have a fixed HTTPS endpoint, bounded time/body, no redirects/proxy and no raw error logging. Database locks/shared cache locks coordinate provider quota pauses; no browser input may bypass a confirmed provider quota. See EMAIL_DELIVERY.md for history/retention and at-least-once limitations.


0.0.27 uses configured/allowlisted canonical origins, safe escaped per-request Inertia JSON, fixed build-owned HTML fragment paths and metadata generation independent of user-agent detection. Build fragments contain no personal user/session data. Stage/local/incomplete builds are nonindexable and private-route noindex is an additional discovery policy, never a substitute for authentication or tenant boundaries. No search-provider credentials, tracking scripts or external migration requests are introduced by the landing page.
